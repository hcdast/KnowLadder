## 2. 每次开发的固定步骤

以下是每个阶段内的工作步骤，不是额外的产品阶段。

| 步骤 | 要做什么 | 离开本步骤的条件 |
| --- | --- | --- |
| D1 现状核对 | 阅读计划、上次验证证据和目标源码，检查已有未提交工作；区分真实实现与原型 | 明确本次起点、已完成项、缺口及不能覆盖的已有修改 |
| D2 范围与设计 | 明确目标、非目标、依赖、权限/数据风险；简单修订可直接执行，跨模块/新阶段先判断设计需求 | 需要设计时先取得用户确认，再补齐设计并确认可执行；计划不能替代授权 |
| D3 拆分任务 | 使用本计划中的稳定任务编号，明确契约、文件范围、验收方法与依赖；只把实际开工项标为进行中 | 有可执行任务及可观察的完成标准，不提前创建空模块或占位实现 |
| D4 实现 | 修改源代码并迁移必要调用方，维护权限、事务、版本和错误处理，不修改自动生成的 `dist/` | 目标行为贯通；生成类型通过真实 OpenAPI 重新生成，不手改 |
| D5 验证 | 运行对应真实场景；修复需复现并确认不再触发，UI需浏览器操作，持久化需实际服务/数据库证据 | 记录命令、环境、结果及未覆盖项；扫描不可mock成功，失败/跳过不能算通过 |
| D6 Review | 审查范围、正确性、安全、回归与数据保全；修复发现的问题后再审查并补验证 | 无未解决的 Critical/High；其他遗留问题有明确影响与处理记录 |
| D7 同步与交接 | 同步受影响文档、本计划任务状态、证据、风险与下一步，清理本次临时服务 | 新会话只读仓库即可知道完成到哪里、下一步做什么；没有悬空的“进行中”说明 |
| D8 版本管理（可选） | 仅按用户明确授权 commit；push需另外明确授权 | 测试、Review、文档更新均不自动授予 commit/push 权限 |

状态仅使用：**未开始 / 待确认 / 进行中 / 阻塞 / 已完成（本地）**。有代码但未验证必须写明“待验证”，不得直接标已完成。阻塞项须写缺少的前提、已尝试的办法和可恢复入口。阶段完成以验收门槛为准，不按代码量或文档篇幅推算完成百分比。

## 8. 每次文档更新必须同步本计划

此约定适用于参与项目的所有开发者和模型；根目录 `AGENTS.md` 提供持久入口。

1. **更新前核对**：先读本计划当前快照、目标任务与证据。文档是历史记录还是当前事实必须标明；看到某接口的设计不能直接将任务改成已完成。
2. **同一轮同步**：任何项目文档新增、修改或删除，都必须在交付前同步本文件的最近核对日期、计划修订及第9节更新记录。涉及范围、契约、开发进度或验收变化，还须同步对应阶段、稳定任务编号、状态、代码定位、验证结果、风险和下一步；不要留下两套相互矛盾的进度表。
3. **纯文字修订也要记**：若只改措辞、链接或排版，在更新记录明确“仅文档修订，阶段/任务状态不变”及影响文件，不虚构新开发成果，不必重跑无关业务测试。
4. **完成条件不降级**：任务有必要实现及实测证据才标已完成；无法验证应记录已实现/待验证或阻塞。旧的失败证据不删除，不以另一次环境通过改写它。
5. **交接必须落盘**：本轮结束前写清已完成项、剩余项、阻塞原因、下一项稳定任务编号和启动条件；短暂任务清单、模型记忆、聊天消息或临时服务不替代仓库内记录。
6. **避免重复真相**：技术/API/模型细节维护在对应方案和源码，本文件维护当前状态与任务索引；`docs/README.md`和根README只提供入口及简要说明。同步本计划本身只记一次，无须为了同步递归生成新的更新记录。
7. **授权独立**：新阶段实施、生产部署、不可逆数据操作、commit与push均按各自授权判断；计划中的下一步不是自动执行许可。
